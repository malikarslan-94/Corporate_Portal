2. Purpose

This document establishes a single, reviewable definition of the User Management component. It records what the portal currently does, identifies behavior that is uncertain or defective, proposes a controlled target behavior, and supplies acceptance tests that can be used by development, QA, and management.

The primary business goal is to allow an authorized corporate portal operator to manage end users belonging to the logged-in corporate account without affecting another partner’s data.

3. Scope

3.1 Included

  • Opening and loading the Corporate Users page.
  • Viewing, searching, sorting, paginating, and exporting the user list.
  • Creating a corporate user.
  • Editing an existing user.
  • Activating or suspending a user.
  • Deleting a user, subject to the business decision in Section 19.
  • Viewing, assigning, and removing a corporate payment card association.
  • Opening Support with the selected user prefilled.
  • Validation, API feedback, authorization expectations, audit requirements, and error states related to these actions.
  • Cross-component addendum documenting the Bulk Top-up API sequence and bearer-token ownership rules.

3.2 Excluded

  • Portal login, password reset, and session management except where they control access to this component.
  • The internal Support screen after the selected user is handed off.
  • Order, device, plan, transaction, and inventory workflows, except for the Bulk Top-up API and token-resolution addendum in Appendix C.
  • Corporate Card screen behavior outside assignment/removal from an individual user.
  • Backend database schema and internal API implementation not available in this repository.
  • Bulk user import. No such flow exists in the reviewed component.

9. Flow USR-F01 — Open and Load Corporate Users

AttributeDefinition
StatusAS-IS documented; TO-BE improvements proposed
Primary actorAuthenticated Corporate Portal Operator
TriggerOperator selects Users or navigates to /admin/users.
PreconditionsRedux login state contains Islogin = true; logged-in account has user_id and normally a source.
PostconditionThe current partner’s users are shown, or an empty/error state is shown.

9.1 Current main flow

  1. The route renders the Corporate Users page.
  2. The page calls getCorpUsers using the logged-in user_id as partner_id and the logged-in source.
  3. A loading indicator remains visible until the request resolves.
  4. If status.result is true, the response user array is stored in Redux and shown.
  5. If the response is unsuccessful or the request throws, loading ends and the table normally shows “No users found.”

9.2 Proposed required behavior

  1. The system shall verify that the operator has View Users permission before requesting or displaying user data.
  2. The backend shall enforce partner/tenant scope independently of frontend controls.
  3. Loading, empty, unauthorized, and technical-error states shall be visibly different.
  4. A technical-error state shall include a Retry action.
  5. The page shall never display cached users from a different signed-in corporate account.

9.3 Acceptance criteria

  • USR-AC01: Given an authorized operator and a successful response, when the page opens, then only users returned for that operator’s partner scope are displayed.
  • USR-AC02: Given the request is pending, when the page is visible, then a loading state is shown and destructive actions are unavailable.
  • USR-AC03: Given a successful empty response, then the page displays “No users found” and does not describe the result as a system error.
  • USR-AC04: Given a network or server failure, then the page displays an error with Retry and does not incorrectly claim there are no users.
  • USR-AC05: Given an unauthorized operator, then navigation and direct route access are denied and no user-list request succeeds.

10. Flow USR-F02 — Search, Sort, Paginate, and Export

10.1 Current behavior

  • Search matches case-insensitive text across visible user data fields in the already-loaded list.
  • Sorting is client-side and toggles ascending/descending.
  • Pagination is client-side.
  • CSV export support exists in the table, but is currently not activated on this page because of a prop-name mismatch.

10.2 Proposed required behavior

  • Search shall match First Name, Last Name, Email, Contact, Promo Code, Source, and Status.
  • Clearing search shall restore the full loaded list and reset to page 1.
  • Changing page size shall reset to page 1.
  • CSV export shall exclude the Actions column and internal implementation fields unless specifically approved.
  • CSV export shall respect the current search and sorting result.
  • Export permission shall be independently configurable if user data is considered sensitive.

10.3 Acceptance criteria

  • USR-AC06: Searching by a partial email returns matching rows regardless of letter case.
  • USR-AC07: Sorting a column twice changes from ascending to descending.
  • USR-AC08: The row range and total count match the current filtered result.
  • USR-AC09: Export produces one row per filtered user and no Actions column.
  • USR-AC10: A user without Export permission cannot export user data.

11. Flow USR-F03 — Create User

AttributeDefinition
TriggerOperator selects + Add User.
PreconditionsOperator is authenticated and is permitted to create users.
Required visible inputs todayFirst name, Last name, Work Email/User ID, Phone number, Status.
Read-only visible inputCorporate Email, populated from logged-in account ID.
PostconditionA new user is created for the intended partner and appears once in the list.

11.1 Current main flow

  1. The add modal opens with blank names/email, country calling code 65, Active status, Singapore defaults, English language, SGD currency, user type CNS, source urwifi, and no corporate card.
  2. The operator enters first name, last name, email, and phone.
  3. The operator may change status.
  4. Selecting Create user checks only that first name, last name, email, and phone number are non-empty.
  5. The component posts the profile to addCorpUser with requestType: Add.
  6. On success, res.user is appended to the current Redux user list and the API message is shown.
  7. The modal remains open after success.

11.2 Current exceptions and gaps

  • Email format is not reliably enforced because the button invokes JavaScript outside a form submit flow.
  • Whitespace-only values can pass the truthy checks.
  • Phone length and validity are not explicitly checked.
  • The isCreatingUser state is never set, so the Create button is not protected against repeated clicks while the API call is pending.
  • The request source is always urwifi, even when the logged-in portal source differs. This requires business confirmation.
  • The modal fetches card data on mount even though a new user does not yet have an email or app user ID.

11.3 Proposed required behavior

  1. Trim all text inputs before validation and submission.
  2. Require valid first name, last name, email, and international phone number.
  3. Reject duplicate email/user ID within the applicable source according to the backend uniqueness rule.
  4. Disable the Create button and show progress while the request is pending.
  5. Create exactly one user even if the operator double-clicks or the network retries.
  6. On success, close the modal, display confirmation, and show the created row without a full-page reload.
  7. On failure, keep entered values, show a clear error, and allow retry.
  8. Do not request payment-card data before the user exists.

11.4 Acceptance criteria

  • USR-AC11: Blank or whitespace-only required fields block submission and show field-level guidance.
  • USR-AC12: An invalid email blocks submission.
  • USR-AC13: An invalid/incomplete phone number blocks submission.
  • USR-AC14: While creation is pending, a second request cannot be submitted.
  • USR-AC15: A successful response closes the modal and displays exactly one new row.
  • USR-AC16: A duplicate-user response displays an understandable message and preserves entered data.
  • USR-AC17: The created user is linked only to the approved partner/source scope.

12. Flow USR-F04 — Edit User

12.1 Current main flow

  1. The operator selects Edit for a row.
  2. The modal loads the row’s values. First name, last name, and status are editable.
  3. Email/User ID, Corporate Email, and phone are disabled.
  4. Hidden profile values are included in the save payload.
  5. The operator selects Save.
  6. The component posts to addCorpUser with requestType: Edit.
  7. On success, the matching Redux item is mutated using email and app user ID, and card information is refreshed.

12.2 Current exceptions and gaps

  • The modal subtitle always says “Create a new user” even in Edit mode.
  • The Redux reducer mutates the existing array/object and returns the same state object, so the user table may not re-render reliably after an edit.
  • Edit uses the logged-in account’s source rather than the selected row’s request_source. This may be correct for single-source tenants but is unsafe without confirmation.
  • There is no dirty-state warning if the modal is closed after changes.
  • Success does not close the modal.

12.3 Proposed required behavior

  1. The modal shall accurately identify Edit mode.
  2. Immutable identifiers shall remain read-only unless a separate, approved migration flow exists.
  3. The system shall submit only the selected user’s authoritative partner/source identifiers, not inferred defaults that can move or overwrite a cross-source user.
  4. The Save action shall be disabled until a value changes and while saving.
  5. Closing with unsaved changes shall request confirmation.
  6. On success, the table shall immediately reflect the saved values.
  7. Concurrent modification shall be handled by a version/update timestamp or a clearly documented last-write-wins decision.

12.4 Acceptance criteria

  • USR-AC18: Email and phone cannot be edited through this flow.
  • USR-AC19: Save sends the selected user’s ID and approved source/partner scope.
  • USR-AC20: The list updates immediately after a successful save.
  • USR-AC21: A failed save retains the operator’s changes and displays the backend message.
  • USR-AC22: Closing a dirty modal requires confirmation.

13. Flow USR-F05 — Suspend or Reactivate User

13.1 Current behavior

  • A Suspend icon is available for an active user.
  • Selecting it immediately sends an Edit request with active: 0; there is no confirmation.
  • The icon shows a loader for that row while pending.
  • On success, the row is updated locally and the action becomes disabled.
  • On failure, no visible success/error notification is shown.
  • A suspended user can be reactivated by opening Edit and choosing Active.

13.2 Proposed required behavior

  1. Suspend shall require confirmation that states the expected effect on login, orders, devices, plans, and billing.
  2. The system shall prevent repeated submissions while pending.
  3. Success and failure shall be visibly communicated.
  4. Suspension shall preserve the user record and history.
  5. Reactivation shall be an explicit permitted action with the same audit requirements.
  6. The business owner shall confirm whether suspension immediately blocks user authentication and new purchases.

13.3 Acceptance criteria

  • USR-AC23: Canceling the confirmation makes no request and changes no status.
  • USR-AC24: Confirming suspension changes the status to Suspended only after backend success.
  • USR-AC25: A failed suspension leaves the displayed status unchanged and shows an error.
  • USR-AC26: The audit record contains actor, user, old status, new status, timestamp, and reason if required.
  • USR-AC27: An authorized operator can reactivate a suspended user when the approved policy permits it.

14. Flow USR-F06 — Delete User

Approval required: management must decide whether permanent deletion is permitted. Until the data-retention, financial-record, order-history, and privacy implications are confirmed, Suspend should be the default reversible action.

14.1 Current main flow

  1. Delete User is available in Edit mode.
  2. The operator is shown a Yes/No confirmation.
  3. Yes sends the profile to /jane/deleteUser.
  4. A successful response shows “User has been deleted successfully.”
  5. The component attempts to dispatch a delete action and closes the modal after three seconds.

14.2 Current critical gap

The dispatched DELETEUSER action is not defined in authActions and there is no delete case in the authentication reducer. The frontend list therefore may continue showing the deleted user until the page reloads. If the API rejects deletion, the modal still closes after the delay. If the request throws, the error is logged but processing state and feedback are not reliably reset.

14.3 Proposed required behavior

  1. If hard deletion is prohibited, remove this action and use Suspend/Archive only.
  2. If deletion is approved, the confirmation must state that the action is irreversible and list blocked conditions.
  3. The backend shall refuse deletion when retention rules or dependent records require preservation.
  4. The UI shall remove the row only after confirmed backend success.
  5. A rejected or failed deletion shall keep the user and modal state unchanged and show the reason.
  6. The operation shall create an immutable audit event.

14.4 Acceptance criteria

  • USR-AC28: No delete request is sent without explicit confirmation.
  • USR-AC29: A successful approved deletion removes the row exactly once.
  • USR-AC30: A rejected deletion keeps the row visible and shows the reason.
  • USR-AC31: Users with protected financial/order history follow the approved retention rule.
  • USR-AC32: Unauthorized operators cannot see or invoke Delete.

15. Flow USR-F07 — Assign Corporate Card

15.1 Current behavior

  1. This option is shown only in Edit mode when the selected user does not already have a card with payment gateway crpc.
  2. The operator checks “Assign corporate card to user.”
  3. If the logged-in corporate account has no corp_card, Save is blocked with “Corporate card does not exists.”
  4. On Save, isAssignCard is true only when no current card ID was found and the checkbox is selected.
  5. The user edit and card assignment are submitted through the same addCorpUser request.

15.2 Proposed required behavior

  • The UI shall clearly identify the corporate card being assigned using masked information only.
  • Assignment shall require Card Assignment permission.
  • The operation shall be idempotent and prevent multiple corporate-card associations unless multiple cards are explicitly supported.
  • Failure to assign the card must not falsely report the entire user edit as successful. Atomic versus partial behavior must be defined.
  • Full card numbers, tokens, or sensitive authentication data shall never be displayed or logged.

15.3 Acceptance criteria

  • USR-AC33: Assignment is unavailable when the corporate account has no eligible card.
  • USR-AC34: A user with an existing corporate card cannot receive a duplicate assignment.
  • USR-AC35: Successful assignment displays only masked card information.
  • USR-AC36: Assignment creates an audit event identifying actor, user, masked card reference, and timestamp.

16. Flow USR-F08 — Remove Corporate Card

16.1 Current behavior

  1. If a crpc card exists, the modal displays masked last digits and a Delete button.
  2. Selecting Delete shows a Yes/No confirmation titled Delete Card.
  3. Yes sends cardId, user email, and app user ID to the remote dispatcher.
  4. On success, a message is shown and card data is refreshed.

16.2 Proposed required behavior

  • Business wording should be Unassign corporate card unless the backend actually deletes a stored payment method.
  • The confirmation shall explain whether future billing fails, changes to another method, or remains on corporate billing.
  • Removal shall require Card Assignment permission and an audit event.
  • Failure shall leave the displayed association unchanged and show a recoverable error.

16.3 Acceptance criteria

  • USR-AC37: Canceling confirmation leaves the association unchanged.
  • USR-AC38: Successful removal replaces the masked-card display with the assignment option.
  • USR-AC39: A failed removal preserves the card display and shows an error.

17. Flow USR-F09 — Open User in Support

17.1 Current behavior

  1. The Support action is enabled only when the row has an email.
  2. Selecting it navigates to /admin/support with prefillUserQuery containing the email.
  3. The Support page copies the email into its query, runs an Email/Mobile user search, and clears the navigation state.

17.2 Proposed required behavior and acceptance criteria

  • USR-AC40: Selecting Support for a user with an email opens Support and initiates the correct user lookup.
  • USR-AC41: The Support action is disabled with an explanatory tooltip when email is absent.
  • USR-AC42: Support authorization and partner scope are checked independently; navigation context must not grant access.

C.4 Current Token Defect — TOP-G01 (AS-IS)

Problem: The current getBearerToken(payload) returns the cached end-user token only when its email matches the first identity-like payload value. In every other case it returns the logged-in admin token. It does not require the admin token’s email to match the payload email.

Example failure scenario:

  1. The logged-in operator is corporate@example.com, and the stored admin token belongs to that email.
  2. Device D-1001 is assigned to customer@example.com.
  3. topupRequest correctly puts customer@example.com in the payload’s userId.
  4. No cached janeuser token exists for customer@example.com, or the cached token belongs to a different end user.
  5. The current resolver falls back to the admin token for corporate@example.com.
  6. The API therefore receives a payload for customer@example.com with a bearer token belonging to corporate@example.com. Because a truthy token was returned, the dispatcher does not fetch the customer’s token.

A second defect is that the current payload resolver accepts the first non-empty identity-like field without confirming that it is an email. For getJaneUsers, it can select the device ID from user_id before reaching the corporate email in corp_id.

C.5 Proposed Global Token Rule (TO-BE)

The application shall use one universal rule based on the final request payload. The rule shall not require individual screens to decide whether an admin or end-user token is needed.

IDRequired behavior
TOP-BR01Inspect only approved identity fields and accept a value only when it is a syntactically valid email after trimming and lowercasing.
TOP-BR02If the payload contains a valid email and a cached token has the same normalized email, use that exact token regardless of whether it is currently labelled admin or janeuser.
TOP-BR03If the payload contains a valid email but no exact cached match exists, call /user/getStateData for that email and source.
TOP-BR04Store a successfully fetched token together with the same normalized email, then use it for the original request.
TOP-BR05If token retrieval fails or returns no usable token for an email-bound protected request, abort that request and return a clear error. Do not substitute another identity’s token.
TOP-BR06If the payload contains no valid email, do not add an Authorization header. Do not silently use the logged-in admin token.
TOP-BR07Never send Bearer null, Bearer undefined, an empty bearer value, or a bearer token known to belong to another email.
TOP-BR08All service callers shall await token resolution before building and sending the request.
TOP-BR09The token decision shall be made from the final API payload after request mapping, so the identity used for authorization is the identity actually sent to the endpoint.
TOP-BR10Token-fetch failures shall be handled per device in Bulk Top-up, allowing the result table to identify the failed device without applying the plan under the wrong identity.

C.6 Proposed Resolver Design

The following is reference logic for implementation review. Exact naming may change, but the rules in C.5 must remain true.

const EMAIL_FIELDS = [
  'userId', 'user_id', 'email',
  'partnerId', 'partner_id', 'corp_id', 'corpId'
];

function isValidEmail(value) {
  return typeof value === 'string' &&
    /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value.trim());
}

export function resolvePayloadEmail(payload) {
  for (const field of EMAIL_FIELDS) {
    const value = payload?.[field];
    if (isValidEmail(value)) return value.trim().toLowerCase();
  }
  return '';
}

export async function getBearerToken(payload) {
  const email = resolvePayloadEmail(payload);
  if (!email) return null;

  const { admin, janeuser } = store.getState().janeuser?.tokens || {};
  if (admin?.email === email && admin?.token) return admin.token;
  if (janeuser?.email === email && janeuser?.token) return janeuser.token;

  const token = await getTokenData({ userId: email, source: payload?.source });
  if (!token) throw new Error(`Unable to obtain a token for ${email}`);
  return token;
}

Each service wrapper shall then await the resolver and add the header only when a token exists:

const bearerToken = await getBearerToken(finalPayload);
const headers = { 'Content-Type': 'application/json' };
if (bearerToken) headers.Authorization = `Bearer ${bearerToken}`;
Important implementation impact: Changing getBearerToken to an asynchronous resolver affects every current caller, including the generic service wrappers, dispatcher, API client, and any direct component calls. Each caller must be audited and updated to await the result. The implementation must also prevent recursive token fetching when getTokenData itself calls getStateData.

C.7 Resulting Bulk Top-up Token Sequence (TO-BE)

For each device: 1. getJaneUsers payload contains device ID + corporate email → Skip device ID because it is not an email → Resolve exact corporate-email token → Fetch it through getStateData only if not cached 2. getUserCardsEnc payload contains corporate email → Reuse/fetch exact corporate-email token 3. topupRequest payload contains assigned owner email → Reuse exact owner token when cached → Otherwise call getStateData for that owner email → Save and use the returned owner token → If no owner token is obtained, do not call topupRequest 4. Record the device result and continue according to the batch policy

This means the card lookup intentionally uses the corporate user’s token, while the final top-up intentionally uses the assigned device owner’s token. The selection is derived from each payload’s valid email; it is not hard-coded by screen or endpoint.
